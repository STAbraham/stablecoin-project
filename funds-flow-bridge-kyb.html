Product: a dollar-denominated store-of-value account for Zed's existing, KYC'd Philippine credit cardholders. Users fund in PHP from their own bank accounts; Zed converts to USD and acquires OUSD (issued by Open Standard, via Bridge) into the user's self-custody Privy embedded wallet. Store of value only — no payments, no external crypto transfers. Pilot scope: 50 invite-only users · pilot-wide TVL cap ≈ ₱15M (≈ $260k) · per-user balance cap ≈ $8,700.

On-ramp: PHP → OUSD (steps 1–3) Off-ramp: OUSD → PHP (steps 4–7) Treasury float rebalancing (T) Rewards (R)

Flow detail

On-ramp — PHP → OUSD

  1. 1User sends PHP from their own bank or e-wallet (QRPH scan or bank transfer) to their dedicated Netbank virtual collection account, used exclusively for dollar-account funding.
  2. 2Deposit is auto-matched to the user and order; PHP settles into Zed's PHP float. Unmatched or out-of-limit deposits alert ops within 15 minutes; default remedy is refund to source.
  3. 3Zed locks the FX rate quoted to the user, debits its pre-funded USD float at Bridge, and acquires OUSD via Bridge, delivered on-chain to the user's Privy self-custody wallet. Each on-ramp records PHP in, rate, spread, USD funded, OUSD out, and tx hash.

Off-ramp — OUSD → PHP

  1. 4User authorizes (Privy signing) an OUSD transfer from their wallet to Zed's redemption address.
  2. 5Zed redeems OUSD → USD via Bridge; proceeds land in Zed's Bridge balance, replenishing the USD float.
  3. 6The PHP payout is funded from Zed's PHP float at Netbank — the user does not wait on redemption settlement.
  4. 7Netbank's Disburse-to-Account API pays the user's own, name-matched PH bank account — InstaPay for < ₱50k (near-real-time), PESONet above. Each off-ramp records OUSD redeemed, USD received, rate, spread, PHP sent, rail, and rail reference.

Treasury & rewards

  1. TFloats are rebalanced daily: net PHP collected is converted to USD (and vice versa) manually on the FX venue's own interface — Coins.ph (BSP-licensed VASP) or a partner bank — dual-approved and ledger-recorded. Ramps execute instantly against floats and never wait on FX.
  2. ROUSD reserve yield is paid to Zed at the platform level (per Open Standard's distribution program; Open Standard fee ≤ 25bps of yield). Zed passes rewards through to users in OUSD on a monthly distribution, computed from on-chain balance snapshots, fully auditable.
  3. 8US/EU off-ramp (gated): per-user enablement via support; redemption as in 4–5, then Bridge's own fiat rails to the user's own US/EU account. No Zed FX or float involved.

Controls & compliance posture

  • KYC: every pilot user is already KYC'd via Persona as a Zed cardholder; KYC data is shared with Bridge at onboarding to create the Bridge customer (users complete only any delta Bridge requires).
  • Own-account-only fiat legs: deposits originate from, and payouts go to, bank accounts in the user's own name (name-match enforced; third-party payouts excluded) — minimizing mule/AML surface.
  • Closed loop: Zed's app is the only interface to the Privy wallet — no external crypto send/receive surface, no deposits from outside the Zed ecosystem shown. Store of value only: no payments, P2P, or merchant spend.
  • Transaction monitoring: on/off-ramp events feed Zed's existing monitoring and screening stack (incl. Comply Advantage) used for the card program.
  • Destination-account data encrypted at rest and masked everywhere; full account numbers materialized only at disbursement time.
  • Double-entry ledger over all Zed-controlled funds (floats, in-flight amounts, spread, rewards pool); append-only, balanced postings for every ramp, rebalance, and rewards event.
  • Daily three-way reconciliation: internal ledger vs. Bridge / bank / FX-venue statements vs. on-chain OUSD across user wallets. Any break pages ops; the pilot runs a zero-loss bar (no break unresolved > 24h).
  • Dual control on every manual money movement (treasury rebalance, manual disbursement, refund): one operator initiates, a second approves, all audit-logged.
  • Per-operation state machines: every ramp has an immutable event trail; terminal states only completed, refunded, or failed-with-ops-resolution.
  • Halt procedure: documented "close the ramp" runbook — on-ramps can be disabled at any time while off-ramps keep working (withdrawal-priority posture).
